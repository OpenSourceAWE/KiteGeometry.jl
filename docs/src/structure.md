# System definition

A `SystemDefinition` holds one awesIO structure document. Its component types are generated by `src/build.jl` from the schema vendored at `src/awesio/structure_schema.yml` from the awesIO commit `gen/awesio.toml` records: one field per required column, in the schema's order, then one per optional awesIO column, which is `nothing` where a document leaves it out, each quantity's unit in its docstring. A document writes an optional column only where a row fills it. Segments, tubes and a wing's canopy name their material, a row of the `materials` block. Blocks the schema does not name are kept in `extras`; a column it does not name is read only as a field of a registered model.

```@docs

Metadata
load_structure
structure_document
```

## Frames

Positions are in the ENU world frame, with the kite at zenith by convention. Each wing gives the origin and rotation of its KA frame, the frame its aerodynamic mesh is drawn in, and `pos_KA` puts a world position into it.

```@docs
pos_KA
```

## YAML and JSON

A document is read and written in either encoding, through `SystemDefinition(document)` and `structure_document`, whose docstrings say which `awesIO_version` and `connectivity_sha` each accepts and writes. What a round trip of a real system still loses is listed in [1-Bart-1/awesIO#3](https://github.com/1-Bart-1/awesIO/issues/3).

## Logs

A KiteUtils log carries a system definition as JSON in its metadata under the key `topology`. Saving a log with the definition writes it there, and `KiteGeometry.definition` reads it back from the loaded log or from the string itself.

```@docs
KiteGeometry.KiteUtils.save_log(::KiteGeometry.Logger, ::SystemDefinition)
KiteGeometry.definition
```

## SymbolicAWEModels' authoring YAML

SymbolicAWEModels authors a system in its wing's KA frame: points at `pos_cad`, tethers by their segment count and stretched length, `variables` shared between rows, and `transforms` that turn the whole to an elevation, azimuth and heading. `load_authoring` converts that dialect into a `SystemDefinition` with the kite at zenith, so `structure_document` writes it as the full-form document. Each segment's stiffness and density become a `linear` material and a tube's `breukels2011` law SymbolicAWEModels' Breukels constants. The columns the schema left to tools, such as a point's `type` and drag, are read only by the models SymbolicAWEModels registers. A `canopy_faces` table with the schema's own columns states each wing's canopy: a face's wing, and its corners by name or index. A filled cell that neither the loader nor the row's model reads is refused, as `load_structure` refuses one, naming the block and its columns, and so is a block it does not read that holds rows; a row's `idx`, where it has one, must be its position. A column a dict row leaves out is an unset cell, which a model field holds only where it admits `nothing`.


## Models

Every component `T{M}` carries a `model::M`: the parameters a tool attaches to a row by naming a registered model in its `model` column, one extra column per field of `M`, in the units the model was registered with. A table without a `model` column reads the model registered for its block with `default=true`; the writer leaves the `model` column out where every row reads that default, and names each row's model otherwise. A row whose `model` cell is unset or names no registered model, or whose table has no `model` column and whose block has no default, is a `NoModel` component. A model column a table leaves out is unset, refused where its field cannot be `nothing`, and the writer leaves out a model column no row fills. Reading refuses a filled cell in a column neither the schema nor the row's model names, an unregistered model's name included; `strict=false` drops those columns with a warning instead. A component reaches its model's fields as its own, so `tube.EA` reads `tube.model.EA`.
