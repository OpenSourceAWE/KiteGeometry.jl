# System definition

A `SystemDefinition` holds one awesIO structure document and the system document it names: the system file owns the design, the materials and each tether as a whole, and the structure its discretisation. Its component types are generated by `src/build.jl` from the schemas vendored at `src/awesio/` from the awesIO commit `gen/awesio.toml` records: one field per required column, in the schema's order, then one per optional awesIO column, which is `nothing` where a document leaves it out, each quantity's unit in its docstring. A document writes an optional column only where a row fills it. Segments, tubes and a wing's canopy name their material, a row of the system's `materials`; the system's tethers are its `system_tethers`, each sharing its name with the tether of a structure that discretises it, and `system_extras` keeps what else the system holds. Each table block's rows are `Rows`, found by their position or their name: `system.points[:kite]`. Blocks the schema does not name are kept in `extras`; a column it does not name is read only as a field of a registered model.

## One system, several structures

`load_structure` reads a structure with the system file its `metadata.system` names, relative to the structure, and refuses a `metadata.system_sha` that is not the hash of that file's bytes. Several structures may name one system, which holds the materials and tethers of them all. Writing that system takes every definition and refuses one name with two different values; writing each structure then takes the system's path and hash:

```julia
system_text = to_yaml(system_document([beam, psm]; name="v3_kite", description, note))
write("system_config/v3_system.yml", system_text)
sha = system_sha("system_config/v3_system.yml")
write("structure/v3_beam_structure.yml",
      to_yaml(structure_document(beam; system="../system_config/v3_system.yml",
                                 system_sha=sha, note)))
```

## YAML and JSON

A document is read and written in either encoding, through `SystemDefinition(document, system_document)`, `structure_document` and `system_document`, whose docstrings say which `awesIO_version` and `connectivity_sha` each accepts and writes. YAML is written valid under 1.2 and read the same by 1.1 readers: a string that could read as anything else is quoted, and a float has its point and its exponent's sign. What a round trip of a real system still loses is listed in [1-Bart-1/awesIO#3](https://github.com/1-Bart-1/awesIO/issues/3).

## Logs

A KiteUtils log carries a system definition as JSON in its metadata, the structure under the key `topology` and the system under the key `system`, so a run loads again from the log alone. Saving a log with the definition writes them there, and `KiteGeometry.definition` reads them back from the loaded log or from the two strings.

## SymbolicAWEModels' authoring YAML

SymbolicAWEModels authors a system in its wing's KA frame: points at `pos_cad`, tethers by their segment count and stretched length, `variables` shared between rows, and `transforms` that turn the whole to an elevation, azimuth and heading. `load_authoring` converts that dialect into a `SystemDefinition` placed by its transforms, and returns those transforms beside it, so `structure_document` writes the full-form document with no transforms in it. Each segment's stiffness and density become a `linear` material of the system and a tube's `breukels2011` law SymbolicAWEModels' Breukels constants; each tether a winch holds becomes a tether of the system, of the length of its rest lengths and the diameter and material its segments share, and any other row of `tethers` is a bridle line, whose segments alone reach the structure document. The columns the schema left to tools, such as a point's `type` and drag, are read only by the models SymbolicAWEModels registers. A `canopy_faces` table with the schema's own columns states each wing's canopy: a face's wing, and its corners by name or index. A filled cell that neither the loader nor the row's model reads is refused, as `load_structure` refuses one, naming the block and its columns, and so is a block it does not read that holds rows; a row's `idx`, where it has one, must be its position. A column a dict row leaves out is an unset cell, which a model field holds only where it admits `nothing`.

`KiteGeometry.resolve_material` completes a segment's diameter, stiffness, damping and density from what its row gives and the settings, as the loader does, and `KiteGeometry.unit_stiffness` gives the stiffness of a `linear` material at a diameter, or of a placed segment from its material. `KiteGeometry.expand_tether!` adds a tether's segments and inner points to rows a tool holds, as the loader does for a row that gives a segment count, its stiffness a number, a law's name or a callable force law, collected in a `KiteGeometry.MaterialTable`.

## Transforms

A transform turns some of a system's points and bodies, its members, about a base: what it turns goes to an elevation and azimuth seen from that base, the azimuth running anti-clockwise from east towards north as `atan(y, x)` does, and the body it heads to a heading about the radial. Its base is a point moved to a base position, or what another transform turns, so one transform can be chained on another. The transforms are kept beside the definition rather than in it: `place!` applies changed ones to a definition before a run, and `reposition!` and `transform_velocities` act on a `Pose`, the positions and body frames a run holds.

```julia
system, transforms = load_authoring("kite.yaml"; set)
transforms[1].elevation = deg2rad(40)
place!(system, transforms)
```

## Models

Every component `T{M}` carries a `model::M`: the parameters a tool attaches to a row by naming a registered model in its `model` column, one extra column per field of `M` that `model_columns(M)` names, in the units the model was registered with. A table without a `model` column reads the model registered for its block with `default=true`; the writer leaves the `model` column out where every row reads that default, and names each row's model otherwise. A row whose `model` cell is unset or names no registered model, or whose table has no `model` column and whose block has no default, is a `NoModel` component. A model column a table leaves out is unset, refused where its field cannot be `nothing`, and the writer leaves out a model column no row fills. Reading refuses a filled cell in a column neither the schema nor the row's model names, an unregistered model's name included; `strict=false` drops those columns with a warning instead. A parametric model registers its `UnionAll`, read through the outer constructor `M(columns...)` the tool defines, and the writer names every instance of it after that registration. A component reaches its model's fields as its own, so `tube.EA` reads `tube.model.EA` and `tube.EA = 3e5` sets it.
